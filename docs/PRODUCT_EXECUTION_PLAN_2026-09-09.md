# LearnHub 제품 우선순위 실행 계획

대상: 여러 분야를 배우는 일반 성인. 사용자가 요청한 원칙: 쉽고, 보기 좋고, 정확하고, 빠르고, 간편해야 한다. 기존 페이지 구성·노션형 구조를 유지하는 것을 목표로 삼지 않는다.

총괄은 제품 판단·설계·통합 검토를 담당하고, GPT-5.6 Luna High 서브에이전트가 구현한다. 사용자에게 화면·실제 서비스 검증을 맡긴다는 기존 분담을 유지한다. 코드 검사 통과와 사용성·내용 정확성 검증은 서로 다른 상태다.

## 1. 본질적인 문제 정의

사용자는 '커리큘럼을 생성하고 지식 그래프를 관리하는 것' 자체를 위해 방문하지 않는다. 지금 궁금한 것을 이해하거나, 어떤 일을 할 수 있게 되거나, 배운 것을 나중에도 기억하려고 방문한다.

따라서 사용자가 매번 선택해야 하는 기능 수가 아니라, 다음의 작은 성공을 중심으로 서비스를 구성한다.

1. 주제를 말한다.
2. 적당한 분량의 설명과 예시를 이해한다.
3. 한 번 적용하거나 자기 말로 설명한다.
4. 무엇을 했고 무엇이 남았는지 알고 종료한다.
5. 다음에 같은 자리 또는 필요한 복습부터 시작한다.

어려운 설정은 제안값으로 시작하고 필요할 때만 수정하게 한다. 로그인은 저장·기기 이동의 필요가 생겼을 때 설명하고, 학습 시작의 필수 장애물로 두지 않는다. 레슨을 끝내도 모르는 점이 남을 수 있으므로 '완료'를 '완벽한 실력'과 혼동하지 않는다.

## 2. 정보 구조를 줄이는 방향

주 내비게이션은 **홈 / 기록**으로 줄이고, **학습**은 홈에서 이어지는 작업 화면으로 다룬다. 이는 코드의 모든 화면 분기를 당장 세 개로 삭제한다는 뜻이 아니다. 기존 기록과 기능을 보존하면서 주요 경로를 단순하게 만드는 단계다.

| 기존 기능 | 새로운 주요 위치 | 사용 이유 |
|---|---|---|
| 새 과목 만들기 | 홈의 주제 입력 | 모달을 열고 같은 주제를 다시 입력하는 중복 줄이기 |
| 진행 중 과목 | 홈의 이어서 학습 | 복귀 사용자는 새 과목 생성보다 기존 위치가 우선 |
| 오늘의 복습 | 홈의 작은 할 일 / 학습 진입 | 학습 중 이동 경로를 새로 익히지 않게 하기 |
| 레슨·질문·연습 | 학습 화면과 보조 패널 | 본문을 떠나지 않고 막힌 부분 해결 |
| 오답·성과 | 기록 안의 선택 섹션 | 다른 이름의 여러 페이지를 돌아다니지 않게 하기 |
| 프로필·백업·연결 상태 | 기록의 설정 영역 | 매 학습마다 볼 필요 없는 정보 분리 |
| 수학 진단·예시 지도 | 선택적인 보조 기능 | 범용 성인 학습의 필수 단계로 오해하지 않게 하기 |

중요: 기능을 숨기는 것만으로 단순해지지는 않는다. '기록' 안에서도 완료 내역·다시 볼 내용·저장 상태를 쉽게 구분해야 한다. 카드 수와 장식 요소를 늘리는 리디자인은 우선하지 않는다.

운영 지표와 학습자 정보를 분리한다. 첫 레슨 방문 수·과목 생성 수 같은 퍼널 숫자는 제품 운영에는 유용하지만, 학습자의 기본 화면을 차지할 이유는 없다. 기본 기록 화면은 끝낸 레슨·다시 볼 개념을 우선하며, 진단용 로컬 사용 기록은 선택적으로 펼치게 한다.

## 3. 디자인·속도·정확성의 판단 기준

| 원칙 | 실행 기준 | 실제 확인 방법 |
|---|---|---|
| 쉬움 | 한 화면에 가장 중요한 행동 하나가 구분됨 | 처음 방문한 사람이 설명 없이 첫 학습을 시작하는지 관찰 |
| 간편함 | 같은 입력을 반복하지 않고, 설정은 선택적으로 펼침 | 홈 주제 제출부터 첫 레슨까지 중복 입력·불필요한 확인 수 기록 |
| 보기 좋음 | 읽기 편한 본문, 일정한 간격·색·버튼 위계, 작은 보조 글씨에 핵심 정보 숨기지 않음 | 실제 화면·휴대전화·확대 상태에서 사용자가 확인 |
| 빠름 | 불필요한 중복 생성·자동 재시도 없음, 기다리는 상태와 취소 명확 | 요청 수·지연·실패율 측정; 측정 전 '빨라졌다'고 단정하지 않음 |
| 정확함 | 구조 검증·분야별 허용 범위·판정 불가·오류 신고 구분 | 고정 회귀 사례와 분야 전문가 내용 검수 병행 |
| 믿을 수 있음 | 저장·신고·검수·동기화 성공을 실제 성공 이후에만 표시 | 실패·중단·재진입 시 거짓 성공 메시지가 없는지 확인 |

첫 화면 체감 속도와 AI 생성 속도는 분리한다. 화면을 빨리 보여주더라도 잘못된 대체 콘텐츠로 생성 성공을 꾸미지 않는다. 모든 미래 레슨을 선제 생성하거나 사용자가 원하지 않은 AI 호출로 대기시간을 감추지 않는다.

## 4. 우선순위별 이번 실행 범위

### 1순위: 분야별 제공 범위와 학습 성공 기준

- 현재 LearningType 다섯 가지의 지원/미지원 범위와 작은 성공 기준을 코드의 공통 정의로 만든다.
- 계획 미리보기와 레슨에 핵심만 보여주며, 설정 문항을 늘리지 않는다.
- 언어의 발음 평가·코드의 실제 실행처럼 제공하지 않는 기능은 명시한다.
- 파이썬·여행 일본어·사진·미술·분수의 고정 사례와 잘못된 응답 사례를 만든다.
- 구조 검증 통과는 사실성·학습 효과 인증이 아니라는 경계를 유지한다.

### 2순위: AI 콘텐츠 검수와 오류 신고 기반

- 커리큘럼/레슨 구조, 빈 콘텐츠, 선택지·정답의 일관성을 서버와 화면 경계에서 검증한다.
- 레슨 위치와 분류를 지정하는 간단한 신고 창을 제공한다. 답안·대화 전체를 몰래 첨부하지 않는다.
- 서버에 실제 저장된 경우에만 접수 번호를 표시한다. 연결되지 않았거나 실패하면 '이 기기 임시 저장·미접수'로 안내한다.
- 접수는 검수 완료가 아니다. 내용 검수자와 수정·재검수 담당자는 별도로 정해야 한다.

### 3순위: 계정·기록·공개 API 보호

- 공급자 선택 전에도 안전한 백업·복원, 데이터 버전·충돌 확인, 인증/영속 저장 연결 경계를 준비한다.
- 실제 인증이 연결되지 않은 공개 실행에서는 AI API를 기본 차단한다. 개발 예외는 루프백 접속으로 제한한다.
- 입력 크기·요청 빈도·동시 요청·출력 길이·일일 호출량을 제한하고, 내부 오류를 사용자에게 그대로 내보내지 않는다.
- 요청 ID·시간·상태·사용량 정보만 관측하며 원문·인증 토큰을 로그에 남기지 않는다.
- 프로세스 메모리 기반 제한은 재시작/여러 서버에 걸친 영구적인 과금 상한이 아니다. 공개 운영에서는 공유 제한 저장소와 실제 제공업체 비용 설정을 따로 확인한다.

### 4순위: 재방문·학습 효과 측정 준비, 앱 확장 조건

- 원문·이메일을 수집하지 않는 로컬 이벤트로 시작·종료·복습 재진입의 관찰 기반을 만든다.
- 샘플·개인 과목, 읽기 완료·문항 판정, 방문·실제 학습을 구분한다.
- 하루 작업으로 재방문율이나 학습 효과를 입증하지 않는다. 실제 사용 기간과 내용 검수가 필요하다.
- 네이티브 앱 출시는 이 결과와 실제 계정/기기 복구를 확인한 뒤 판단한다. 이번 단계는 앱 출시가 아니다.

## 5. Supabase/Firebase를 반드시 써야 하는가

아니다. 필요한 것은 '확인된 사용자에게 자기 기록만 제공하는 서버 기능'이지 특정 제품이 아니다. 별도 백엔드와 데이터베이스, 검증된 인증 라이브러리로 구성할 수도 있다.

- Supabase는 PostgreSQL 및 인증과 연결되는 행 단위 접근 정책을 제공한다. 과목·레슨·문항·학습 기록의 관계를 다루는 후보라는 판단이지 자동으로 더 적합하다는 확정이 아니다. [공식 접근 정책 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Firebase의 Firestore는 오프라인 접근 및 연결 복구 후 동기화 기능을 제공한다. 이것도 서비스의 충돌·권한 정책 전체를 자동으로 해결한다는 뜻은 아니다. [공식 오프라인 문서](https://firebase.google.com/docs/firestore/manage-data/enable-offline)
- 별도 백엔드는 구조를 직접 통제하는 대신 인증·권한·백업·복구·운영 책임을 더 맡는다. 암호 기술을 직접 발명하자는 뜻이 아니라 검증된 구성 요소를 연결하고 운영한다는 뜻이다.

현재 사용자가 선택 이유를 질문했으므로 **공급자 채택은 미확정**이다. 프로젝트 생성·유료 결제·클라우드 배포·외부 데이터 업로드는 하지 않는다. 코드에서 이를 실제 연결 완료로 표현하지 않는다.

총괄 의견: 현재 단계에서는 관리형 인증·데이터 저장을 활용하고, LearnHub의 학습·채점·품질 로직은 기존 Express 서버에 두는 혼합 구성을 권한다. Supabase Auth/PostgreSQL이 후보이며, 관계형 학습 기록을 다루기 적합하다는 프로젝트 구조에 따른 판단이다. 무조건 더 싸거나 응답이 더 빠르다는 뜻은 아니다. 사용자가 장단점을 확인 중이므로 이 의견을 채택 승인으로 간주하지 않는다.

관리형에서도 데이터 접근 정책과 애플리케이션 보안은 우리 책임이다. 별도 운영에서는 서버 유지보수·백업·복구·모니터링 책임이 추가된다. [관리형 책임 범위](https://supabase.com/docs/guides/deployment/shared-responsibility-model), [직접 운영 책임](https://supabase.com/docs/guides/self-hosting)

## 6. 사용자의 도움이 필요한 지점

1. 인증/DB 운영 방식: 관리형 서비스를 활용할지, 기존 서버를 활용할지 결정. 기존 계정·서버가 있다면 그 맥락을 먼저 확인한다.
2. 외부 연결 단계: 프로젝트 URL과 공개 클라이언트 설정, 로그인 방식과 리디렉션 주소. 비밀 키를 대화에 붙여넣지 않고 환경 설정으로 관리한다.
3. 콘텐츠 운영: 초기 주력 분야와 검수 가능한 사람/자료, 신고 확인 책임자를 정한다.
4. 실제 사용 검증: 화면·기기·AI 응답을 확인하고, 사용 후 불편과 학습 효과를 기록한다.

개발 중 선택이 필요한 다른 사안은 근거와 영향이 있을 때만 질문한다. 기존 데이터 삭제나 외부 전송을 사용자에게 묻지 않고 처리하지 않는다.

## 7. 실행 결과

GPT-5.6 Luna / High 서브에이전트 4개가 구현하고 총괄은 기획·코드 통합 검토를 수행했다. 화면·실시간 서비스 검증은 사용자 담당으로 유지했다.

### 로컬 구현 완료

- 홈·학습 기록을 주요 탐색으로 정리하고 고급 기능은 선택 영역에 유지했다. 홈에서 입력한 주제로 계획 생성을 시작하며, 과목 생성 창의 hook 순서 오류와 중복 자동 생성 위험을 수정했다.
- 다섯 학습 유형의 제공 범위·성공 기준, 커리큘럼/레슨 구조 검증, 다섯 분야 고정 사례를 추가했다. 퀴즈 단계의 누락된 문항과 객관식 선택지·정답 불일치를 거부한다.
- 오류 신고 창과 같은 학습 위치의 초안 불러오기를 추가했다. 실제 접수·미접수 초안·로컬 저장 실패를 구분한다. 현재 공급자 미연결 상태에서는 실제 접수가 아니라 로컬 초안이다.
- 사용자 주도 백업 파일 저장·불러오기, 충돌 미리보기, 현재 데이터 유지/합치기/덮어쓰기를 추가했다. 합치기에서는 유효한 기존 진도·메모 등을 보존하고, 가져오기 전 백업 다운로드를 제공한다. 복구 자체가 실패하면 복구 성공으로 표시하지 않는다.
- 인증·영속 저장 연결 인터페이스와 공개 환경의 기본 차단, 개발 환경의 루프백/Host/Origin 검사, 사용자별 요청 제한, 동시 실행·일일 요청·출력 토큰 예약 제한을 추가했다. 로그에는 원문이나 인증 토큰을 남기지 않는다.
- 샘플을 제외한 로컬 학습 행동 기록을 추가하고 운영 진단용 집계는 접힌 영역으로 분리했다. 학습 기록의 예상 시간은 실제 집중 시간과 구분한다.
