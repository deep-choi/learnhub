# LearnHub 페이지 구성과 구현 상태

## 제품 기준

대상은 학습하고 싶은 전 연령이다(2026-09-29 변경, 이전: 일반 성인). 메뉴를 기능별로 계속 늘리지 않고 `배울 주제 선택 → 학습 → 이해 확인 → 마무리 → 복습`을 짧게 연결한다. 화면이 존재하는 것, 실제 계정/서버에 연결된 것, 사용자 검증이 끝난 것은 별개로 판정한다.

## 필요한 주요 화면

| 화면 | 사용자에게 필요한 이유 | 구현 판단 기준 |
| --- | --- | --- |
| 홈 | 배우고 싶은 주제 입력, 기존 과목 시작/이어가기 | 첫 방문 빈 상태와 과목 생성 직후에도 다음 행동이 명확함 |
| 학습 작업 화면 | 설명·예제·확인 문제, 메모와 질문 | 저장 실패·판정 불가·재시도 및 종료가 명확함 |
| 복습 | 오늘 다시 볼 내용과 틀린 개념 점검 | 예정일과 실제 판정 기록에 기반해 동작함 |
| 학습 기록 | 완료한 공부·개념별 기록·오답 확인 | 읽기 완료와 이해/숙달을 혼동하지 않음 |
| 계정 및 설정 | 로그인·로그아웃, 기록 저장/복원, 로컬 백업 | 실제 세션, 데이터 소유자, 충돌, 실패 상태를 구분함 |

주 메뉴는 홈/학습 기록으로 유지한다. 복습은 홈의 예정 복습 진입점, 학습은 과목에서 진입, 설정은 보조 메뉴로 제공한다. 이는 화면 역할이 다섯 개라는 뜻이지 같은 비중의 메뉴를 다섯 개 만든다는 뜻이 아니다.

## 별도 페이지로 늘리지 않는 기능

- 과목 만들기와 계획 확인: 입력/미리보기 모달. 자세한 설정은 선택.
- 로그인: 계정 화면과 로그인 모달. 초기 방식은 이메일 링크이며 소셜 로그인은 미연결 상태에서 버튼으로 성공을 흉내 내지 않는다.
- 학습 종료: 완료 모달에서 읽기 완료/확인 문제 상태와 다음 행동 안내.
- AI 튜터·오류 신고·메모: 현재 학습 위치를 유지하는 패널 또는 모달.
- 과목별 목차: 홈/과목 탐색에 통합. `CourseDetailView.tsx` 파일 존재만으로 활성 페이지라고 세지 않는다.
- 지식 지도·세부 실력표·진단·타이머: 기존 보조 기능으로 유지하되 핵심 여정의 필수 단계로 만들지 않는다.

## 공개 출시 전 별도로 결정/준비할 화면

| 항목 | 현재 범위 | 남은 준비 |
| --- | --- | --- |
| 개인정보·이용 안내 | 운영 문서와 제품 UI는 다름 | 실제 수집 데이터, AI 전송 범위, 보관/삭제 정책, 운영자 정보 확정 후 게시 |
| 도움말·문의 | 레슨 오류 신고는 일반 문의를 대체하지 않음 | 실제 문의 채널과 응답 책임자 연결 |
| 계정 삭제·클라우드 데이터 삭제 | 로컬 초기화와 별개 | 재인증, 삭제 범위, 복구 가능성, 서버 처리 검증 |
| 콘텐츠 검수 관리 | 신고 접수와 검수 완료는 별개 | 운영자 권한과 신고 목록, 수정/재검수 흐름 |

초기에는 개인정보/이용 안내와 도움말을 작은 안내 영역으로 묶을 수 있다. 실제 운영 정보가 없는 문구를 정식 정책이나 검수 완료로 표시하지 않는다. 관리자 화면은 학습자 메뉴에 노출하지 않는다.

## 이번 작업 검증 결과

### 외부 구성 확인

- Supabase LearnHub 프로젝트 `rfyaulzkzxuvyejxbecz`: 서울 리전, Free 조직, Healthy 상태 확인.
- 기존 Dayflow는 변경하지 않았다. 이전 GitHub 저장소 `study`도 변경하지 않았다.
- `learning_snapshots`, `content_reports` 테이블과 `put_learning_snapshot` RPC를 실제 DB에 최초 생성했다. 최초 실행은 삭제/교체 구문 없이 수행했고, 재실행용 SQL은 저장소의 migration 파일에 별도 보관한다.
- 실제 DB 카탈로그 검사에서 두 테이블 모두 RLS 활성/강제, 익명 SELECT 불허, authenticated TRUNCATE 불허를 확인했다. 이 검사는 실제 두 계정 간 접근 테스트를 대신하지 않는다.
- 로컬 `.env.supabase`에는 공개 URL과 publishable key만 저장했다. `.gitignore`에 의해 제외되며 DB 비밀번호나 service-role key를 사용하지 않는다.
- 개발 서버 재시작 후 `/api/public-config` 200과 예상 프로젝트 일치, `/api/learning-snapshot`의 비로그인 요청 401을 확인했다.
- 로그인 Site URL은 `http://localhost:3000`, 추가 Redirect URL 없음, custom SMTP 꺼짐을 읽기 전용으로 확인했다. 메일 발송/로그인 완료는 사용자 테스트가 필요하다.

### 구현상 경계

- 현재 클라우드 저장은 검증된 백업 문서를 계정별로 저장/불러오는 초기 방식이다. 자동 동기화나 학습 기록의 최종 정규화 구조가 아니다.
- 로그인만으로 게스트 기록을 업로드하지 않는다. 저장/복원은 사용자가 명시적으로 선택하며 다른 계정에 연결된 로컬 기록은 자동 이전하지 않는다.
- 서비스 화면은 코드로 개선하며 시각·실기기 검증은 사용자가 담당한다. 타입 검사와 빌드 통과만으로 사용성·접근성·사실성 검증 완료라고 판단하지 않는다.
- SDK 설치 중 발견된 의존성 경고는 허용 범위 내 수정 후에도 `express`/`qs` 관련 moderate 2건이 남았다. 강제 메이저 업그레이드는 하지 않았으며 공개 운영 전 다시 점검한다.

### 사용자 검증 순서

1. localhost:3000 새로고침 → 새 홈/접힌 예시/모바일 메뉴 확인.
2. 주제 입력 → 필요 시 이메일 로그인 → 입력한 주제를 잃지 않고 계획 확인.
3. 학습 설명/예제/퀴즈 → AI 질문 → 완료 → 다음 학습/복습.
4. 계정 및 설정 → 클라우드에 저장 → 같은 계정으로 다른 브라우저 로그인 → 기록 불러오기 미리보기/복원.
5. 원래 브라우저에서 오래된 버전 저장 시 충돌 경고 확인. 계정 전환 시 다른 계정 기록 업로드가 차단되는지 확인.
6. 메일 미도착/네트워크 끊김/로컬 저장 공간 부족 시 성공으로 표시하지 않는지 확인.

### 최종 자동 검사

- 전체 테스트 68/68 통과. 실제 Supabase 계정이나 유료 AI를 호출하지 않는 로컬 자동 검사다.
- `npm run lint`(TypeScript 검사) 통과.
- `npm run build` 프런트엔드 및 서버 빌드 통과. 프런트엔드 단일 JS 청크 약 652 KB(압축 전)로 크기 경고가 있어, 느린 모바일 환경에서는 후속 코드 분할과 실측이 필요하다.
- 홈·학습·복습·기록·계정/설정의 핵심 화면은 코드 구현 및 연결이 완료됐다. 이메일 로그인과 계정별 클라우드 저장/복원은 실제 사용자 검증이 남았다.
- 개인정보/이용 안내, 일반 도움말/문의, 실제 계정 삭제, 운영자 콘텐츠 검수 화면까지 포함한 공개 출시 전체 범위는 아직 완료되지 않았다.
- 서비스 화면의 브라우저 시각 검증, 실기기 검증, 실시간 AI 품질 검증, 배포는 이번 검사에 포함하지 않았다.
